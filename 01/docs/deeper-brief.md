# 01 深化題目（草稿，Claude 版）

> 狀態：記錄用，尚未套用到設計文件（2026-11-03）。
>
> 來源：使用者要求「更深入，而不是更大」，請 Claude 回答四個問題後改寫題目。Codex gpt-6.1-terra 對同一組問題的回答另外比較。

## (1) 頂尖專家會做、但沒被要求的事

- **先講清楚真正的問題。** Pod 被關掉時，有兩件事同時開始、互不等待：Kubernetes 通知入口（Gateway 底下的 Envoy）「別再送流量給這個 Pod」，以及通知程式「準備關機」。所有短連線的失敗都來自這個時間差。每次量測都要在時間線上讓學生看到這兩件事的先後，而不只是看到成績單上的失敗張數。
- **參數用量的，不用猜。** `preStop` 該等幾秒，等於「入口實際花多久才停止送流量」，在 tk8s 上量出來再加緩衝。心跳間隔也一樣，從 Envoy 實際的設定讀出逾時值來決定。
- **實驗要能被推翻。** 每一步先寫下預測；每個條件跑好幾次，回報範圍，不只看一次的數字。還要有兩組對照：
  - **不升級的對照組**：必須 0 失敗。不是的話，表示雜訊來自量測工具或環境本身。
  - **步驟 0 基準組**：必須量到失敗。量不到的話，表示這個實驗根本偵測不到問題，後面「修好了」也就不成立。
- **失敗要用原始證據分類。** 同樣是送單失敗，可能是 Envoy 連不到 Pod、Pod 處理到一半被切斷，也可能是 Rush Hour 自己逾時。每一種都有對應的原始紀錄可以查。
- **證明對帳程式自己是對的。** 故意弄壞程式，例如讓它漏送一個叫號，確認對帳程式真的抓得到。
- **驗證學到的東西能用在別處。** 同一套修正，在 `kubectl drain`（清空節點）和縮減 Pod 數量時也要成立。學生學的是 Pod 終止，不只是滾動更新。

## (2) 從哪些原始素材入手

| 素材 | 要回答的問題 |
|---|---|
| Kubernetes 的 Pod 終止流程文件、EndpointSlice 的 terminating 狀態（KEP-1672）、kubelet 原始碼 | `preStop` 和 SIGTERM 的實際順序；終止中的 Pod 會不會繼續收流量 |
| Cilium 把 Gateway API 轉成 Envoy 設定的原始碼，以及 tk8s 上 Envoy 的即時設定（config dump） | 入口實際的逾時值、重試設定，以及多久才拿掉終止中的 Pod |
| Envoy 文件裡的回應旗標和各種逾時 | 每一個 503 屬於哪一種失敗 |
| Go `net/http` 原始碼（`Shutdown`、`RegisterOnShutdown`，以及用戶端對 POST 不會自動重試） | 關機和重試行為是否和設計假設一致 |
| WHATWG HTML 規格的 SSE 章節 | `Last-Event-ID`、`retry`、空事件會不會觸發 |
| PostgreSQL 文件：`NOTIFY` 的送達時機和順序、sequence 不受交易回滾影響、advisory lock | 叫號編號的保證有沒有真正的依據 |
| CNPG 文件 | operator 升級或設定變更會不會重啟資料庫，影響量測 |
| 每次量測當下的原始紀錄：Kubernetes events、EndpointSlice 變化、Hubble 流量紀錄、Envoy access log、App log、Rush Hour 每個請求的紀錄 | 重建事件時間線，不靠推論 |

## (3) 具體的方法和工具

- **時間線重建。** 同時記錄下面這些來源，再合併成一條時間線。所有節點都是同一台主機上的 podman container，共用同一個時鐘，所以時間戳可以直接比較。
  - `kubectl get events -w` 和 `kubectl get endpointslice -w`
  - `hubble observe`
  - Envoy 管理介面的 stats，例如 `upstream_rq_503`、`upstream_cx_destroy_remote`
  - App 和 Rush Hour 輸出的 JSONL 紀錄
- **固定速率的負載。** Rush Hour 依時間表送單，不等上一張回應才送下一張。這樣系統變慢時不會跟著少送，避免把問題藏起來（coordinated omission）。再用 k6 或 vegeta 跑一次，交叉比對 Rush Hour 的數字。
- **重複實驗。** 每個條件跑 5 次以上，回報中位數和範圍。
- **注入故障。**
  - 用 `kill -STOP` 模擬卡住的 Pod；
  - 刻意暫停 `LISTEN` 連線，模擬漏掉通知；
  - 讓一台看板讀得很慢，模擬寫入卡住；
  - 用 `go test -race` 檢查程式裡的競爭情況。
- **歷史紀錄檢查。** 把每台看板收到的叫號序列和資料庫的完成紀錄逐一比對，檢查有沒有漏、有沒有重複、順序對不對。概念和 Jepsen 檢查分散式系統的方法相同，Go 有 Porcupine 這類工具可以參考。
- **教學方法。** 採用「預測 → 觀察 → 解釋」：學生先寫下猜測，再看成績單和時間線。

## (4) 除了 Claude 和使用者之外，什麼可以證明結果正確

- **原始紀錄互相對得上。** Rush Hour 算出的失敗張數，要和 Envoy stats、access log 對得上；叫號以資料庫為準。
- **另一套工具得到同樣的結論。** 用 k6 或 vegeta 量同一個步驟，結果的方向要一致。
- **正反對照都成立。** 不升級時 0 失敗、步驟 0 一定量到問題；而且故意弄壞程式時，檢查程式一定抓得到。
- **別人可以重現。** 另一個人在全新的 tk8s 上，只照 README 操作，得到相同的定性結果。
- **有上游的依據。** 每個關鍵假設都附 Kubernetes、Envoy、Go、PostgreSQL 的文件或原始碼出處。

## 改寫後的題目

> **01：Pod 終止時，流量和程式各走各的**
>
> 在 tk8s 上，用可重複、可推翻的實驗，讓學生親眼看到：Pod 終止時，「入口停止送流量」和「程式開始關機」同時發生、互不等待。接著量化每一步修正，對短連線（點餐、出餐）和長連線（SSE 叫號看板）各有什麼效果。
>
> 1. **先畫因果時間線**：每次量測都從叢集的原始紀錄產生一條時間線，包含 SIGTERM、EndpointSlice 標為 terminating、Envoy 拿掉這個 Pod、最後一個請求進來、程式結束。每個時間點都要有紀錄作為依據，不是推論。
> 2. **參數由量測推出**：`preStop` 秒數等於實測「入口停止送流量」延遲的上緣，再加緩衝；閒置逾時從 Envoy 的即時設定讀出。
> 3. **實驗可以被推翻**：每一步先寫預測；每個條件至少重複 5 次，回報中位數和範圍。不升級的對照組必須 0 失敗，步驟 0 必須量到失敗；兩者不成立，整個實驗就不成立。
> 4. **失敗用原始證據分類**：依 Envoy 回應旗標、App log 和資料庫對帳，把失敗分成「入口送到正在關的 Pod」「請求處理到一半被切斷」「量測工具自己的問題」。Rush Hour 的數字要能和 Envoy stats 對得上。
> 5. **對帳程式本身要被驗證**：看板不漏號、不重複，以資料庫紀錄逐一檢查；並故意弄壞程式，證明對帳程式抓得到。
> 6. **能用在其他情況**：同一套修正，在 `kubectl drain` 和縮減 Pod 數量時也要成立。
> 7. **能被別人重現**：另一個人在全新的叢集上，只照 README 操作，得到相同的定性結論。每個關鍵假設都附上游文件或原始碼的出處。
