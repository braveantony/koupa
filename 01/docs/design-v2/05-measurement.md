# 5. 量測方法

## 5.1 每次都量同一個方向

各步驟的主要比較都只量 **v1 → v2 的升級**，步驟之間才能公平比較；步驟 4 之後另外做一次退版驗證，結果分開報告（見本節最後）。如果輪流量升級和退版（rollback，回到前一版），數字下降時就分不清是修正的效果，還是方向不同造成的。

Pod 關機時怎麼處理，是由**被關掉的那個 Pod** 的設定決定的。所以要先讓舊 Pod 帶上這一步的設定，再量升級：

```
measure.sh step-N（預設重複 5 次，每次都從第 1 點開始）
  1. 套用 step-N，映像檔設為 v1，等 rollout 完成（不量）
  2. 核對所有 Pod 都已經是 v1，而且帶著 step-N 的設定
  3. 開始收集時間線的原始紀錄
  4. 啟動 rush-hour，看板都連上之後開始送單（預設送 60 秒）
  5. 第 10 秒把映像檔改成 v2                      ← 量這次
     結束前 10 秒還沒 rollout 完成，這次量測無效
  6. 停止送單，收尾，印出成績單，存好證據包
```

所有模式都用同一個送單時段（預設 60 秒，可以調整，但同一組比較必須相同），數字才能互相比較。

量測遵守六個原則：

- **固定方向**：只量 v1 → v2；
- **重複**：每個條件至少量 5 次，逐次列出送單數和各項結果，再列中位數和範圍。5 次是教學用的最低重複次數，可以呈現每次之間的差異，但不保證看得出方向，也估計不了很少發生的失敗率；
- **對照**：`measure.sh control` 套用步驟 0 的設定、全程不升級，必須 0 失敗、0 漏號、0 重複。不成立時，`measure.sh` 停止正式比較，查出原因再繼續（講師可以用診斷模式繼續收集資料，但那些成績單不能拿來比較）；原因可能在量測工具、環境，也可能在 App 本身。控制組的每個項目都要能判定，有「未知」就不算通過。另外，步驟 0 的自然負載必須至少觀察到一種預定的問題；每一種問題也都要在對應的關鍵時機實驗（5.5）裡，呈現機制關閉和打開的差異。某個問題在自然負載裡沒觀察到，就只能說「機制在受控實驗中有效」，不能說「這一步在自然負載下改善了它」；
- **量測前核對**：設定不符合就不量；
- **失敗就標示無效**：部署、設定核對或 rollout 失敗，或對帳需要的關鍵資料不足時，成績單標示「本次量測無效」，不印出可能誤導的數字。收尾逾時的個別項目只列為「無法確定」，其他成績照常列出；
- **以資料庫對帳**：漏號和重複訂單都以資料庫裡的紀錄為準。

學生上課照步驟順序量。講師課前驗證時，用 `measure.sh all` 把各條件交錯執行（control、步驟 0、1、2…輪流，重複 5 輪），避免主機負載隨時間變化，被誤當成某一步的效果。

核對清單、失敗條件和時間參數見[實作計畫 A8](../plan.md)。

步驟 4 做完後，再加一次「最終驗證」：`measure.sh rollback` 量一次 v2 → v1，讓學生驗證退版時的送單失敗和漏號情況。

## 5.2 Rush Hour 的角色

Rush Hour 依**固定速率**送單：照時間表送出，不等上一張回應。系統變慢時它不會跟著少送，問題才不會被藏起來。

Rush Hour 在主機上用 podman 執行，從叢集外經過 Gateway 連進來，跟真實客人走同一條路。它產生的流量一樣會消耗 Gateway、App 和資料庫的資源。

每次量測都有一個量測編號，寫在每個 `client_ref` 的開頭，對帳時只看這次量測的訂單。每一次嘗試（包括重試）另外有自己的嘗試編號，App 和 Rush Hour 都會記下來，才分得出同一張單的第一次和第二次送出。

**預設負載**（都可以用參數調整，例如 `--rate 50`）：

| 角色 | 行為 |
|---|---|
| 客人 | 每秒送出 20 張訂單，每張隨機 1～4 杯。送出失敗或逾時，就用同一個 `client_ref` 和同樣的內容重試 1 次 |
| 廚房 | 像真的店員一樣，定期讀取「製作中」清單，每張單看到後隨機 1～3 秒標記完成。所以「客人以為失敗、其實已經建立」的訂單也會被做完 |
| 看板 | 3 台，照瀏覽器 `EventSource` 的規則連線：遵守 `retry:`、自動重連、帶上 `Last-Event-ID`。記下第一個 `hello` 的起點，以及收到的每個 `ready_seq` |

## 5.3 成績單的定義

**每個結果分開看**：一張單、一個叫號，拆成幾個可以各自觀察的結果，不混成一個「失敗」。

| 對象 | 分開觀察的結果 | 一定要成立的條件 |
|---|---|---|
| 點餐 | 每次嘗試：有沒有送到 App → App 有沒有寫出回應 → 客人有沒有收到回應；整張單：交易有沒有提交、資料庫最後有幾張單 | 打開防重複時，同一個 `client_ref` 最多一張單 |
| 出餐 | 每次嘗試：有沒有送到 App → 有沒有配發 `ready_seq` → 店員有沒有收到回應 | 同一張訂單最多配發一個 `ready_seq` |
| 叫號 | 看板有沒有斷線 → 重連後有沒有補送 → 每台看板最後有沒有收到每個叫號 | 每台看板收到的編號遞增、不重複 |

判斷不出來的結果標成「未知」並寫明原因，不當成功，也不當失敗。下面的主要成績都從這些結果算出來；有未知項目時，成績寫成「已確認 N；另有 M 項未知」，不印成單獨的 0。

成績單分成兩區：學生主要看「主要成績」，「診斷資訊」要加上 `--verbose` 才顯示。

**主要成績**

| 項目 | 怎麼算 |
|---|---|
| 訂單 | 這次量測送出的訂單數，每個 `client_ref` 算一張 |
| 送出沒有成功回應 | 第一次送出就沒拿到成功回應（錯誤或逾時）的張數；其中重試後仍沒拿到的張數。訂單可能其實已經建立，所以和「重複訂單」分開看 |
| 重複訂單 | 資料庫裡有兩張以上訂單的 `client_ref` 數，以及多出來的訂單張數 |
| 大螢幕漏號 | 每台看板分開算：這次量測完成的叫號中，在該看板起點之後、而且資料庫裡確實存在，但看板沒收到的數量 |

每次量測印一張成績單；重複 5 次後，另外印一張彙整表，列出每一次的數字、中位數和範圍。

**診斷資訊**

- 每次失敗嘗試**看得到的狀態**：沒送到 App、送到了但 App 沒有結束這個請求、客人沒有收到完整回應但 App 回報寫入和 flush 成功、App 寫入失敗、客人收到錯誤回應；
- 原因：只有證據齊全時才寫，例如「入口在 Pod 開始終止後仍選了它」「請求處理到一半，程式就結束了」。證據不足或有好幾種可能時標「未知」，附上原始紀錄。主機資源吃緊不當成原因，只標成「同時觀察到」的環境狀態。判定規則見[實作計畫 A10](../plan.md)；
- 大螢幕斷線，分成「收到 `shutdown` 後斷線」和「沒收到 `shutdown` 就斷線」兩種。後者也可能是通知在傳送途中遺失，所以不直接推論原因；
- 無法確定的項目：還在途中的請求、還沒完成的訂單、沒追上最後叫號的看板、查詢失敗的項目。這些不算進主要成績，也不能當作零；
- 程式收到 SIGTERM 之後，才送到這個 Pod 的請求數。步驟 1 以後如果不是 0，表示 `preStop` 的候選秒數需要調查：可能是秒數不夠，也可能是既有連線上的請求或紀錄延遲；
- 時間線（見 5.4）和 rollout 結果；
- 主機的 CPU 和記憶體使用量。節點和 Rush Hour 在同一台主機上，資源吃緊時，失敗可能來自量測環境本身。

**收尾**：停止送單後，先等還在途中的請求和重試結束，再確認 App 端每一筆都已經處理完（客人放棄等待，不代表店裡沒做完），讓廚房把剩下的單做完，再等每台看板收到這次量測的最後一個叫號，最後才對帳。每一段都有等待上限，超過上限的項目列為「無法確定」。收尾的詳細步驟見[實作計畫 A9](../plan.md)。

重複訂單有兩種來源：

- 訂單已經存進資料庫，但回應沒送到客人手上，客人重送；
- 第一個請求還在處理，客人等太久就重送，兩個請求同時建立訂單。

兩種都要剛好碰上連線出問題，自然負載下可能很少發生。所以重複訂單的保證不靠 Rush Hour 證明，而是用 5.5 的關鍵時機實驗刻意製造；Rush Hour 只回報自然負載下實際發生了幾次。

## 5.4 因果時間線

每次量測都從叢集的原始紀錄產生一條時間線，讓學生看到問題**可能**發生在哪個時段，不只看到「幾張」：

```
時間 ─────────────────────────────────────────────►
Pod 1   開始終止  （有 preStop 就等它結束）SIGTERM   程式結束
入口           ……還在送流量……   不再送給 Pod 1
請求       #812 進 Pod 1 ──✗ 程式結束，沒有回應
看板 2                        斷線 ── 重連到 Pod 3 ── 補送 3 個
```

上圖是示意。實際上有些點只知道落在某個區間內，或因為缺少紀錄而標成「未知」。

- 每個點都要有原始紀錄作為依據：Kubernetes events、EndpointSlice（Kubernetes 記錄 Service 有哪些後端、各自是否正在終止的物件）的變化、入口（Envoy）的紀錄、App log、Rush Hour 每次嘗試的紀錄；
- 分清楚兩種時間：**事件發生的時間**（例如 API server 收到刪除請求的時間），和**收集端看到的時間**（例如 `kubectl get -w` 收到變化的時間）。後者會晚一點，時間線上要標明用的是哪一種；
- 只知道「在某兩個時間之間」的事件畫成區間；完全取不到的來源，時間線上註明缺少什麼，不畫成精確的點；
- 各來源的紀錄用 `client_ref`、嘗試編號、`order_id`、`ready_seq`、Pod UID 和量測編號串起來；
- 所有節點都是同一台主機上的 container，共用同一個時鐘，跨來源的時間可以直接比較，但仍要考慮記錄和傳遞的延遲。同一個程式內的時間差，用單調時鐘量。

步驟 1 的 `preStop` 秒數，由 `measure.sh calibrate` 量出「開始終止 → 入口最晚已經不再選它」的上界，取得不到上界的樣本不採用，做法見[實作計畫 A11](../plan.md)。量出來的是**這個環境的候選值**：5 次的最大值不是未來的上限。所以之後每次量測都會檢查「SIGTERM 之後才到的請求」（5.3 診斷資訊），一出現就調查是否需要重新校正。

**證據包**：每次量測存一份到 `evidence/<量測編號>/`，內容包括時間線、manifest、版本、映像檔 digest（映像檔內容的唯一識別碼，標籤可以被改指，digest 不會）、參數、原始紀錄、對帳用的查詢和結果、失敗案例、缺少的來源，以及成績單。

## 5.5 關鍵時機實驗

有些保證要在特定的一瞬間才會被考驗，自然負載下不一定碰得到。這類情況用測試專用的暫停點刻意製造，讓同一個時機每次都準確重現：

| 關鍵時機 | 機制關閉時預期 | 機制打開時預期 |
|---|---|---|
| 訂單已經提交、回應還沒送出時，客人放棄等待並重送 | 重複訂單 | 拿回同一張號碼牌（步驟 4） |
| 請求處理到一半，程式收到 SIGTERM | 程式立刻結束，用戶端沒有收到完整的成功回應 | 請求完成並回應（步驟 2） |
| 看板剛連上、已經收到 `hello`，App 還沒開始補送時，有新叫號提交 | 不漏、不重複 | 不漏、不重複 |
| 看板斷線期間，有新叫號提交 | 重連後漏掉這個叫號 | 重連後補回（步驟 3） |
| 一台看板停止讀取、寫入真的被擋住時，程式收到 SIGTERM | — | 其他看板照樣收到 `shutdown`，程式在期限內結束（步驟 2） |

第三列不管開關都要成立，因為它考驗的是補送和即時推送的交接（4.2），不是步驟 3 的補號。

- 每一列都規定好暫停、觸發、放行的先後順序，結果才會穩定，順序見[實作計畫 A12](../plan.md)；
- 暫停點只在測試模式打開，正常的步驟量測裡一律關閉，`measure.sh` 量測前會核對；
- 由講師示範或自動化測試執行，學生不用自己操作，只負責預測結果並解釋。

## 5.6 量測工具本身的驗證

成績單是 Rush Hour 算的，所以 Rush Hour 本身也要被驗證。這些都是自動化測試或講師課前的檢查，不是學生每一步要做的事：

- **對帳程式的已知答案測試**：準備好「資料庫裡有哪些叫號」和「看板收到哪些」的資料，答案事先算好，涵蓋單筆和多筆漏號、重複、補回、起點和截止的邊界、空的資料。對帳程式的結果必須和答案一致；
- **實際注入**：刻意讓 App 少送某條連線幾個叫號，或多建一張重複訂單，對帳程式必須抓到。「注入了幾次」和「最後漏了幾個」分開記錄，因為漏送的叫號可能在重連後被補回；
- **協定交叉檢查**：用真正的瀏覽器 `EventSource` 和 `curl -N` 看原始串流，確認 Rush Hour 對 SSE 的解讀和瀏覽器一致；
- **和入口的紀錄對帳**：先挑出可以比的部分，例如同一段時間、同一條路徑、最終的回應，再比 Rush Hour、Envoy access log 和 Envoy 統計三方的數字，並列出差額的來源（客人端逾時、入口內部重試、沒經過入口的請求）。失敗原因的判定也會參考入口紀錄裡的回應旗標；
- **另一套工具**：用 k6 或 vegeta 以相同速率和重試設定，量步驟 0 和步驟 2 的「送出沒有成功回應」，比較兩套工具看到的增減方向和範圍。不一致就調查；一致但沒有改善，也照實記錄，回頭檢討步驟的假設。

## 5.7 其他 Pod 終止的情況

升級只是 Pod 被終止的其中一種原因。步驟 4 做完後，再用同一套修正量兩種情況，驗證學到的是「Pod 終止」，不只是「滾動更新」：

- `kubectl drain` 清空一個 worker；
- 把 replica 從 3 縮成 2。

這兩種情況和升級不完全一樣：drain 可能同時影響其他 Pod；縮減時沒有新的 Pod 補上，剩下的 Pod 要承擔全部流量。所以比的是**同樣的條件**（不漏號、不重複、送出沒有成功回應的張數），數字和升級分開報告。每次量完都會恢復原狀並確認，細節見[實作計畫 A15](../plan.md)（待實測）。
