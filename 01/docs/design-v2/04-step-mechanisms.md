# 4. 每一步修正的機制

學生只改 Kubernetes 的 YAML。程式端的修正事先寫好，預設關閉，用環境變數打開。

YAML 用 Kustomize（在共用 YAML 上疊加差異的工具）一層疊一層，箭頭指向它引用的前一層：

```
base ◄── step-1 ◄── step-2 ◄── step-3 ◄── step-4 ◄── step-5
base ◄── idle-lab
```

`step-3` 會包含 `base`、`step-1`、`step-2` 的設定，再加上自己的改動。想看完整結果可以執行 `kubectl kustomize k8s/steps/step-3`。

| 步驟 | 改什麼 | 預期效果（都待實測） |
|---|---|---|
| 小實驗 | 打開 `SSE_HEARTBEAT` | 觀察閒置的長連線會不會斷、原因是什麼；如果是閒置逾時，再驗證心跳是否有效 |
| 0 | 什麼都不做 | 可能出現送出失敗、漏號、重複訂單 |
| 1 | 加上 `readinessProbe` | 送給還沒準備好的新 Pod 的失敗消失 |
| 2 | 加上 `preStop` 的 `sleep` | 送給正在關閉 Pod 的失敗減少 |
| 3 | 打開 `GRACEFUL_SHUTDOWN`，設定 `terminationGracePeriodSeconds`（關機寬限時間） | 送出失敗接近 0；看板改成收到伺服器通知後重連，但還是會漏號 |
| 4 | 打開 `RESUME_FROM_LAST_ID` | 看板重連後補回漏掉的叫號，預期量測中觀察到 0 個漏號 |
| 5 | 打開 `IDEMPOTENCY_KEY` | 預期量測中觀察到 0 筆重複訂單 |

每一步聚焦一個修正機制，必要的配套設定（例如步驟 3 的關機寬限時間）會一起調整。預期效果是要被實測檢驗的假設：如果量測結果推翻了某一步的效果或順序，就照實修改步驟，不修改數字。

4.1、4.2 是所有步驟共用的基礎，只有 4.2 的「起點」會受步驟 4 的開關影響。這部分要先做對，後面量到的數字才有意義。

## 4.1 標記完成與配發叫號編號

**保證**：

- 店員重按或同時按兩次「完成」，同一張單只會叫一次號；
- **兩筆都成功提交的叫號，編號較小的那筆一定先提交**。

**做法**：把檢查、配號和更新放在同一個交易（transaction，一組不是全部完成、就是全部取消的資料庫操作）裡。先鎖住這張訂單，讓同時按完成的另一個請求排隊等候，再檢查狀態；已經完成就直接回傳原本的結果。還在製作中，就取得一把全程式共用的叫號鎖（PostgreSQL 的 advisory lock，由應用程式自訂用途的鎖），配發 `ready_seq`、更新訂單、送出 `NOTIFY`，然後提交。叫號鎖一直持有到提交，PostgreSQL 也會在提交後才真的送出通知。逐步做法和必測案例見[實作計畫 A1](../plan.md)。

第二個保證是為了避免這種情況：
```
Pod A 配到 ready_seq 10，還沒提交
Pod B 配到 ready_seq 11，先提交 → 看板收到 11
Pod A 才提交 10
看板之後重連時說「我最後收到 11」→ 10 永遠補不回來
```

代價是所有叫號的提交會排隊一個一個來，實測時要確認每秒送出 20 張訂單的負載下，叫號的等鎖時間和出餐延遲可以接受（待實測）。

## 4.2 每個 Pod 怎麼把叫號推給看板

**叫號廣播員**：每個 Pod 有一個廣播員，用一條專用的資料庫連線 `LISTEN`。收到 `NOTIFY`、重新接上資料庫，以及每隔幾秒，它都會去資料庫查出新的叫號，依 `ready_seq` 順序交給這個 Pod 上的每條看板連線。

`NOTIFY` 只是「去資料庫查一下」的提醒。它送出後不會保留，Pod 沒在聽的時候發生的通知就收不到。所以廣播員還會定期查詢：即使漏掉通知，只要資料庫查詢成功，下一次定期查詢就會查到新叫號，再送給**還連著的**看板（查詢和傳送本身還要一點時間）。看板斷線期間的叫號補不補得回來，取決於步驟 4 的開關。

**每條看板連線的起點**：

| 情況 | 起點 |
|---|---|
| 第一次連線，或 `RESUME_FROM_LAST_ID` 沒打開 | 資料庫目前最大的 `ready_seq`；還沒有任何叫號時是 0 |
| 重連，而且開關打開 | 瀏覽器重連時帶來的 `Last-Event-ID`（最後收到的叫號編號，見 [4.8](#48-步驟-4斷線重連後補號)）。格式錯誤或超出範圍就拒絕連線並記錄 |

連線一開始，App 先送出 `hello` 事件，帶上 `id: <起點>`。這樣即使看板一個叫號都還沒收到就斷線，瀏覽器也有編號可以在重連時帶回來。

**交接的保證**：從起點開始，App 先從資料庫補送，再接上即時推送，兩者之間**不漏、不重複**，而且照編號順序送出。看板太慢或寫入失敗時，App 會結束這條連線。重連後能不能補回斷線期間的叫號，要看步驟 4 的開關（4.8）：打開才補，沒打開就從目前最大的編號開始。交接步驟、前提條件和必測案例見[實作計畫 A2、A3](../plan.md)。

**SSE 事件一覽**

| 事件 | 帶 `id` 嗎 | 用途 |
|---|---|---|
| `hello` | 帶，值是起點 | 告訴看板版本，並讓瀏覽器記住起點 |
| `ready` | 帶，值是 `ready_seq` | 叫號 |
| `shutdown` | 不帶 | 伺服器要關閉了，請準備重連（步驟 3） |
| 心跳（`:` 開頭的註解行） | 不帶 | 避免連線被當成閒置（小實驗） |

## 4.3 閒置斷線小實驗

看板連著但一直沒有叫號時，Gateway 或其他網路元件可能會切斷連線，即使沒在升級。這個問題跟升級無關，放進修正步驟會干擾數字，所以獨立出來，放在步驟 0 之前，讓學生先認識「長連線本身就很脆弱」。

入口可能因為「連線太久沒有資料」而切斷，也可能因為「連線存在的時間太長」而切斷。心跳只對前者有效。

**待實測**：先實際觀察切斷的時間，並查看 Cilium 產生的 Envoy（Cilium Gateway 底層使用的代理程式）設定，確認是哪一種逾時。對應的 Envoy 設定名稱寫在講師手冊。

- 如果是閒置逾時：打開 `SSE_HEARTBEAT`，讓 App 定期送出 SSE 註解行（以 `:` 開頭，瀏覽器會忽略）。間隔要小於實際的逾時，再驗證確實不再斷線；
- 如果是總時間上限：改成調整 HTTPRoute 的逾時設定，小實驗的內容也照實際結果改寫。

## 4.4 步驟 0：基準

App 不做任何收尾。Pod 被刪除時，程式收到 SIGTERM 會立刻結束：處理到一半的請求直接中斷，看板的連線也隨著程式結束而斷掉。App 收到 SIGTERM 後只寫一行「收到 SIGTERM」的 log 就結束，不等請求或看板收尾，讓時間線上有這個點；寫這一行可能多花一點點時間。取不到這一行時，程式結束的時間改用其他來源。

## 4.5 步驟 1：readinessProbe

readinessProbe 是 Kubernetes 用來判斷 Pod 能不能開始接收流量的檢查。沒有設定時，容器一啟動 Pod 就是 Ready，EndpointSlice 馬上把它標成可用，入口就會開始送請求過去。對 Koupa 來說，「能接收流量」的條件是：HTTP 伺服器已經啟動、資料庫連得上，而且叫號廣播員的 `LISTEN` 已經生效。`/healthz` 檢查的就是這三件事。

步驟 1 加上：

```yaml
readinessProbe:
  httpGet: {path: /healthz, port: 8080}
  periodSeconds: 2      # 每 2 秒探測一次
  timeoutSeconds: 1
  failureThreshold: 1   # 一次失敗就不 Ready
  successThreshold: 1   # 一次成功就 Ready
```

不設 `initialDelaySeconds`：容器一啟動就開始探測，App 準備好之後最多約 2 秒就會 Ready。

**為什麼放進修正步驟（實測依據）**：原本預期 Go 程式啟動很快，不需要 readinessProbe，只在步驟 0 量到「新 Pod 還沒準備好就接收流量」造成的失敗時才加。在 tkha 上量到了（詳細見 [env-findings 第 9 節](../env-findings.md#9-步驟-2-的-503-與-prestop-重新校正task-23b)；該節用的是重新編號前的步驟編號）：

- 約 28% 的新 Pod（57 個中 16 個）啟動後 5.02～5.03 秒才開始 listen：Pod 的第一個 DNS 查詢在 Cilium 端點還沒取得正式身分時被丟掉，要等解析器 5 秒逾時後重送；
- 沒有 readinessProbe，這些 Pod 一啟動就 Ready，入口送過去的請求得到 `UF`／`Connection refused`，有這種 Pod 的量測，每次多出約 40～70 張「第一次送出沒有成功回應」；
- 這些失敗和舊 Pod 的關閉無關，加長 `preStop` 沒有作用。

**加上之後的實測**（[env-findings 第 10 節](../env-findings.md#10-readinessprobe-成為步驟-1-之後的實測task-23c)）：步驟 1 和步驟 3 各量 3 次，共有 5 個晚 5 秒才 listen 的新 Pod，它們都在 listen 之後約 2 秒才 Ready，入口在 listen 之前一次也沒有選到它們；「送給還沒 listen 的新 Pod」造成的失敗在 6 次量測中都是 0。步驟 1 還剩的失敗來自正在關閉的舊 Pod，由步驟 2 處理。

這個問題放在步驟 0 之後先修，後面各步量到的「第一次送出沒有成功回應」才只反映舊 Pod 關閉的影響。它只代表這個 App 在這個環境量到的問題；換了環境，失敗的比例可能不同，但「Ready 不等於準備好」的道理一樣。

## 4.6 步驟 2：preStop

Pod 開始關閉時，有兩件事**同時**進行：

- 控制平面把這個 Pod 在 EndpointSlice（記錄 Service 有哪些可用 Pod 的物件）裡標成「正在終止」，Gateway 和各節點收到更新後，才會停止把新流量送過來。這需要一點時間才會傳到各處；
- kubelet 執行 `preStop`，執行完才送 SIGTERM 給程式。

`preStop` 加上 `sleep`，讓程式晚幾秒才收到 SIGTERM，給第一件事時間完成。但它不保證新流量一定已經停了，而且收到 SIGTERM 的那一刻還在處理的請求，在步驟 2 依然會被中斷。所以這一步預期是失敗**減少**，減少多少以實測為準。

**用量測決定秒數**：先在 tk8s 上量出 Pod 開始終止後，入口「最晚什麼時候已經不再選它」——也就是停止送流量時間的上界，用入口的端點更新紀錄直接確認，或用探測流量推估（量法見 [5.4](05-measurement.md#54-因果時間線)）——取多次有效量測的最大值，再加緩衝。只知道「最後一次收到請求」的量測不能用，因為那只是下界。推導過程和原始數據寫進實測紀錄，不憑經驗填一個數字。有效量測不夠時不產生候選值，改用講師手冊的保守值，成績單標示「`preStop` 未經校正」。候選值也只代表本環境，之後每次量測都會檢查「SIGTERM 之後才送到的請求」，一出現就先調查來源，再決定要不要重新校正。

`sleep` 的秒數也會占用關機寬限時間（預設 30 秒）。

## 4.7 步驟 3：Graceful shutdown

打開 `GRACEFUL_SHUTDOWN` 後，App 收到 SIGTERM 時會：

1. 停止接受新連線，同時對每條 SSE 連線先送 `retry:`（建議瀏覽器多久後重連），再送 `shutdown` 事件，flush 之後結束這條連線；
2. 等處理到一半的短連線做完；
3. 上面兩件事共用一個期限（`SHUTDOWN_TIMEOUT`）。到期還沒做完，就記錄下來並結束程式。

`preStop` 的等待時間加上 `SHUTDOWN_TIMEOUT`，必須小於關機寬限時間，並留一點緩衝；否則程式還沒收完尾，就會被 Kubernetes 強制終止。

Go 的 `http.Server.Shutdown` 會等所有進行中的請求結束。SSE 也是一般的 HTTP 請求，只是永遠不會自己結束，所以不主動通知它收尾，`Shutdown` 就會一直等到期限，然後回傳逾時錯誤。這就是第 1 點要同時通知 SSE 收尾的原因。逐步做法和必測案例見[實作計畫 A5](../plan.md)。

看板被伺服器結束連線後，瀏覽器會自動重連。入口何時不再把新連線分給這個 Pod、看板多快改連到其他 Pod，都以實測結果為準。

## 4.8 步驟 4：斷線重連後補號

瀏覽器的 `EventSource`（瀏覽器內建的 SSE 用戶端）自動重連時，會在 `Last-Event-ID` 標頭帶上最後收到的 `id`。打開 `RESUME_FROM_LAST_ID` 後，App 把它當作起點，依 4.2 的交接順序補送。例如最後收到 812，重連時就補送資料庫裡 812 之後的叫號。

開關關閉時，App 不理會 `Last-Event-ID`，一律從資料庫目前最大的編號開始，斷線期間的叫號就會漏掉。

「重連後不漏號」的前提：

- 看板已經收到第一個 `hello`（所以有起點）；
- 是同一個頁面的自動重連。重新整理網頁就是一次新的連線，會從「現在」開始接收。

## 4.9 步驟 5：重送不重複下單

點餐頁每次送出訂單前，產生一個隨機的 `client_ref`。網路失敗重送時，沿用同一個 `client_ref` 和同樣的訂單內容。

打開 `IDEMPOTENCY_KEY` 後，建立訂單的交易會先把 `client_ref` 寫進 `idempotency_keys`。這張表的 `client_ref` 有唯一限制，所以兩個請求同時送到不同 Pod，也只有一個能寫入成功；另一個會等先寫的交易結束，再讀出它的結果。

| 情況 | 回應 |
|---|---|
| 第一次送出 | 建立訂單，回傳號碼牌 |
| 重送，內容相同 | 回傳原本的號碼牌，不新增訂單 |
| 重送時第一個請求還在處理 | 等它完成，再回傳同一張號碼牌 |
| 同一個 `client_ref`，內容不同 | 回傳 409（衝突） |
| 等太久（超過 `lock_timeout`） | 交易 rollback 後回傳 503，客人可以用同一個 `client_ref` 安全重送 |

`idempotency_keys` 的資料從**提交後**起算至少保留 24 小時（清理時多留 1 小時，涵蓋交易本身的時間），超過後可能被清除；清除之後才重送，就會被當成新的訂單。開關關閉時，App 完全不使用這張表。交易流程、鎖的順序、清理的邊界情況和必測案例見[實作計畫 A6、A7](../plan.md)。

出餐 `POST /orders/{id}/ready` 已經在 4.1 處理過，重按不會重複叫號，所以這一步只處理點餐。

這一步放在最後，要讓學生知道：Kubernetes 的設定可以減少部分失敗，但不能保證客人一定收到回應，程式仍要能安全地重送。
