# 量測說明

步驟 0～5 和最後驗證都用 `measure.sh` 量。這份文件說明它做了什麼、為什麼要先跑 control、成績單怎麼讀，以及講師實測的完整結果。每一步自己的操作見各步驟的文件。

## 一次量測做什麼

在 `01/` 目錄執行 `./measure.sh <模式>`，例如 `./measure.sh step-2 --runs 2`。腳本會自己套用那一步的設定，不需要手動修改 YAML 或執行 `kubectl apply`。每一次都會：

1. 套用這一步的 YAML，映像檔設成 v1，等 rollout（逐步把舊 Pod 換成新 Pod）完成；
2. 核對 Pod 真的帶著這一步的設定（7 項，終端機印出 `preflight: all 7 checks passed`），不符合就不量；
3. Rush Hour 的 3 台看板都連上之後開始送單（60 秒，終端機印出 `sending started`），第 10 秒把映像檔換成 v2；
4. 收尾、對帳，印出成績單，存好證據包。

`--runs N` 決定重複幾次，預設 5 次；課堂上每一步用 `--runs 2`，講師的正式紀錄用 5 次。2026-11-10 實測，control 和步驟 2～5 一次約 1.5 分鐘；步驟 0、1 收尾時有比較多「結果未知」的請求要等，一次約 3.5 分鐘。

## 量測時開的視窗

每一步都開同樣三個視窗（`<IP>` 的查法見 [README 2. 部署](../../README.md#2-部署)）：

| 視窗 | 內容 | 必要？ |
|---|---|---|
| 終端機 A | `./measure.sh step-N --runs 2` | 必要 |
| 終端機 B | `kubectl -n koupa get pods -w` | 建議 |
| 瀏覽器（例如 desktop container 裡的 Firefox） | 只開 `http://<IP>/board?debug=1` | 選用，只看不操作 |

- 看板要在終端機 A 印出 `sending started` 之前打開。看板只會顯示它連著的時候叫到的號碼。量測前 `measure.sh` 套用設定時 Pod 也會換一輪，看板先斷線再自動連上是正常的。
- 客人、廚房和 3 台看板都由 Rush Hour 模擬，瀏覽器只是讓你看。**量測期間只看看板，不要操作點餐頁和廚房頁**：Rush Hour 的店員會自己按「完成」；自己下的單不在 Rush Hour 的紀錄裡，不會算進成績單。
- `?debug=1` 讓看板底部多一條資訊列：SSE 連線狀態、服務版本和連著的 Pod。

## control（對照組）

control 和步驟 0 一樣用 `k8s/base`，一樣送 60 秒的單，差別只在第 10 秒**什麼都不做**，不升級（`measure.sh` 的 `control` 模式沒有變更）。它和[小實驗](00-idle-lab.md)無關：小實驗看閒置的看板，control 看的是滿載送單時環境本身乾不乾淨。

```bash
./measure.sh control --runs 2
```

**為什麼要先跑**：沒有升級，就不該有送出失敗、漏號或重複訂單。control 只要不是全部 0，表示環境本身（量測工具、主機資源、網路）就會產生失敗，後面各步驟量到的數字就不能算在升級頭上。

**怎麼判斷通過**：每一次的送出失敗、漏號、重複訂單都是 0，而且沒有「未知」、沒有無效。有一次不通過，`measure.sh` 就印出「對照組不成立：…」，停止後面的次數，以結束碼 3 結束（`echo $?` 可以看）。這時不要比較數字；先看終端機的錯誤訊息，以及該次證據包的 `scorecard.txt` 和 `preflight.txt`，再請講師協助排查。

講師的正式紀錄用 `./measure.sh all`：control、步驟 0～5 依序各跑 1 次算一輪，重複 5 輪。control 和各步驟交錯，環境在中途變差時，control 也會量到。`./measure.sh all --dry-run` 只印出順序，不會量。

## 步驟 0 的門檻

步驟 0 也有門檻：所有次數加起來，至少要觀察到一個預定的問題（送出失敗、漏號或重複訂單）。一個都沒有，表示這個環境量不出升級的問題，後面的修正也看不出效果，`measure.sh` 會印出「對照組不成立：步驟 0 的 N 次都沒觀察到預定的問題」並以結束碼 3 結束。

加上 `--diagnostic` 可以在 control 或步驟 0 的門檻沒過時繼續量，但每張成績單第一行會標「診斷模式：對照組不成立，不可用於比較」。步驟 1～5 加上 `--diagnostic` 也會標這一行。

## 成績單

每次量測結束時都會印出成績單。以下是步驟 3 的一次量測結果（2026-11-10，`preStop` 8 秒）：

```
Rush Hour 成績單　量測編號 step-3-20261110-133434-r1-79fb
preStop：8 秒（已依本環境校正）

【主要成績】
訂單：1200 張
第一次送出沒有成功回應：0 張
重試後仍沒有成功回應：0 張
重複訂單（client_ref 數）：0
多出的訂單張數：0 張
大螢幕漏號（每台看板）：
  board-1：21
  board-2：22
  board-3：22
```

- **第一次送出沒有成功回應**（簡稱「送出失敗」）：客人第一次按送出，沒拿到號碼牌的張數。「重試後仍沒有成功回應」是其中重送一次也沒拿到的張數。
- **重複訂單**：同一次點餐（同一個 `client_ref`，點餐頁給每次點餐的代碼）在資料庫裡變成兩張以上；「多出的訂單張數」是多出來的張數。
- **大螢幕漏號**：每台看板分開算，資料庫裡有、但這台看板沒收到的叫號數。

標題下一行是 `preStop` 有沒有經過校正（步驟 2 以後才有；這次量測時還沒有這一行，上面是現在的格式）。寫「preStop 未經校正」表示校正沒有成功，等待秒數是講師手冊的保守值，不是在這個環境量出來的；寫「未知」表示 Deployment 上沒有這個標記，請講師確認。

**「已確認」和「未知」**：判斷不出來的結果不會算成 0，會寫成「已確認 N；另有 M 項未知」，例如 `board-1：已確認 78；另有 1 個叫號未知` 表示確定漏掉 78 個，另外 1 個判斷不出來。這時成績單最上面會多一行「本次有 M 項結果無法確定，見診斷資訊；未標示未知的項目不受影響」。

全部次數量完後，另外印一張彙整表：每一次的數字、中位數和範圍。含未知的項目不算中位數，寫成「無法計算（另有 N 次含未知，未列入）」。

加上 `--verbose`，成績單會多印「診斷資訊」：每次失敗看得到的狀態和原因。

## 證據包

每次量測存一份在 `evidence/<量測編號>/`（不進 git），彙整表在 `evidence/summary-<模式>-<時間>.txt`。先看這幾個檔案：

| 檔案 | 內容 |
|---|---|
| `scorecard.txt` | 成績單 |
| `timeline.txt` | 時間線：彙整可取得的紀錄，列出每個被關掉的 Pod 何時開始終止、何時收到 SIGTERM（Kubernetes 通知程式關機的訊號）、程式何時結束，以及入口最後一次把請求送給它的時間；缺少紀錄時會標示 |
| `failures.json` | 每一筆失敗或結果未知的嘗試 |
| `preflight.txt` | 量測前的設定核對結果 |
| `evidence-index.txt` | 證據包的檔案清單；缺少的部分標 `MISSING` |

其他檔案保留 App 和入口的原始紀錄、Pod 與可用後端清單（EndpointSlice）的變化、Rush Hour 每次嘗試的紀錄，以及套用的 Kubernetes 設定檔和版本資訊。需要深入排查時再查看。

## 參數

| 參數 | 作用 |
|---|---|
| `--runs N` | 重複 N 次（預設 5） |
| `--verbose` | 成績單多印「診斷資訊」 |
| `--duration 秒數`、`--rate 每秒張數` | 調整送單時長（預設 60，至少 30）和速率（預設 20）。同一組比較要用相同的值 |
| `--diagnostic` | control 或步驟 0 的門檻沒過時繼續量；成績單標成不可用於比較 |

## 結束碼和常見錯誤

| 結束碼 | 意思 | 怎麼辦 |
|---|---|---|
| 0 | 正常結束 | — |
| 1 | 某個步驟失敗或逾時，例如「量測前核對不符」：沒有量，或這次量測無效並停下來 | 看終端機的訊息和證據包的 `preflight.txt` |
| 2 | 至少有一次量測無效，例如「rollout 在第 50 秒（D − 10）前沒有完成」 | 無效的那一次不要拿來比較；看該次的 `scorecard.txt` 寫的原因 |
| 3 | control 或步驟 0 的門檻沒過 | 見上面 [control](#control對照組) |

終端機印出「leftovers of an earlier measurement」表示上一次量測被強制中斷，還留著 Rush Hour 的 container 或收集程式；照訊息括號裡的指令清掉再重跑。

## 預期結果

2026-11-10 在 tkha 上的實測（單一主機上的 3 個 control plane＋3 個 worker，都是 podman container；Kubernetes 1.37.2、Cilium 1.20.4）。control、步驟 0、1 是 `measure.sh all` 交錯量測的各 5 次；步驟 2～5 是 `preStop` 改成 8 秒後重跑、和 control 交錯的各 5 次。每次 1200 張訂單。數字是中位數，括號內是範圍。

| 條件 | 第一次送出沒有成功回應 | 重試後仍沒有成功回應 | 漏號（每台看板） | 重複訂單 |
|---|---|---|---|---|
| control（不升級） | 0 | 0 | 0 | 0 |
| 步驟 0 | 51（8～53） | 3（1～6） | 已確認 12～83；4 次另有未知 | 已確認 0；另有未知 |
| 步驟 1 | 7（4～12） | 0 | 已確認 25～164；4 次另有未知 | 已確認 0；另有未知 |
| 步驟 2 | 0 | 0 | 約 80（76～109） | 0 |
| 步驟 3 | 0 | 0 | 約 22（18～41） | 0 |
| 步驟 4 | 0 | 0 | 0 | 0 |
| 步驟 5 | 0 | 0 | 0 | 0 |

你的數字不必和這張表一樣，要比的是**趨勢**：

- control 必須全部是 0 而且沒有未知，才適合比較；這次實測的步驟 0 每次都量到問題；
- 步驟 1 少掉「新 Pod 還沒準備好」那一類失敗；這次實測中，步驟 2 起沒有觀察到送出失敗；
- 漏號到步驟 2 都還在，步驟 3 變少；這次實測中，步驟 4 起沒有觀察到漏號；
- 這次預設負載下沒有確認到重複訂單，要看關鍵時機實驗。

步驟 0 的數字特別不穩定，因為這取決於有沒有碰到晚 5 秒才準備好的新 Pod（見[步驟 1](step-1.md)）。不同環境的結果可能不同。

**結論的邊界**：這些結果只代表單一主機、單一資料庫實例、[實測紀錄](../measurements/2026-11-10.md#1-環境與版本)列出的版本和設定。每個條件只量 5 次，「是 0」的意思是「這 5 次都沒觀察到」，不代表「不會發生」。

量測方法的完整說明見[設計文件 5. 量測方法](../design-v2/05-measurement.md)。
