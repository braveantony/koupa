# 01 深化題目（草稿，Codex gpt-6.1-terra 版）

> 狀態：記錄用，尚未套用到設計文件（2026-11-03）。
>
> 使用者把同一組問題原文交給 Codex gpt-6.1-terra（新 thread，未讀 Claude 版 `deeper-brief.md`）。以下是它的回答，原文照錄。

更深入的關鍵，是把題目從「觀察滾動更新前後的成績」推進到「用可重現的證據，說明特定連線在特定時間點為什麼成功、失敗或結果不明」。這不需要增加付款、會員、更多部署策略或分散式元件；需要的是更精確的問題、對照實驗和驗證方式。

目前文件已經有不錯的基礎：固定 v1 → v2、分步加入機制、用資料庫對帳，也區分了「沒有成功回應」和「沒有建立訂單」。以下建議保留這些設計，同時把尚未驗證的機制視為假說。文件狀態是**設計定案、尚未實作**，所以以下是研究與題目設計建議，不是對環境的實測結論。

## 1. 頂尖專家還會做哪些事？

**先定義可以被推翻的主張。** 例如，「加上 preStop 後，入口立即停止送流量」不能只憑一次成功的成績單成立；要分別觀察 Pod 開始終止、EndpointSlice 狀態改變、入口實際停止選到該 Pod 的時間。Kubernetes 文件描述了終止流程與 endpoint 條件，但在你的 Cilium 版本和設定下，資料平面的實際收斂仍須量測。[Kubernetes Pod 生命週期](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)、[Kubernetes probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)

**拆開連線結果與業務結果。** `POST /orders` 失去回應時，資料庫可能已提交；看板 TCP 斷線也不等於一定漏號。專家會明確區分：請求是否送達、交易是否提交、回應是否收到、是否重試，以及叫號是否最終被看板收到。無法判定的結果維持「未知」。

**刻意製造關鍵時序，而不只等待它偶然出現。** 例如在「訂單提交後、回應前」切斷連線，在 SSE「登記後、查詢補送上界前」提交叫號，在請求處理中觸發終止。這些受控實驗能檢驗正確性；Rush Hour 則用來觀察較自然的更新行為。兩者回答的問題不同。

**檢查量測工具本身。** Rush Hour 與 App 可能共同誤解 SSE 協定，或因紀錄遺失而得到漂亮但錯誤的成績單。專家會用真正的瀏覽器 `EventSource`、原始 HTTP 串流與獨立資料庫查詢交叉檢查，並測試量測工具在刻意漏事件、重複事件及對帳失敗時是否能正確報告。

**檢查反例與保證的邊界。** 例如：重連後補送與瀏覽器實際顯示是不同層次；使用 idempotency key 的保證受 key 保存期限、請求內容與交易邊界限制；單次零失敗不代表永遠不失敗。也要檢查 v1、v2 同時運作時，兩者對事件與資料的理解是否相容。

**以教學價值篩選深度。** 不必讓學生實作所有故障注入工具。可以把受控實驗包裝成講師操作或既有測試，學生仍然練習提出預測、讀取證據、解釋反例。保留現有五步驟，但允許實測推翻某一步的效果或順序。

## 2. 應從哪些原始素材入手？

這裡的「原始」指最接近實際行為或規範的證據；現有設計與計畫仍有用，但應作為**待驗證的假說**。

| 素材 | 要取得的內容與用途 |
|---|---|
| 實際叢集狀態 | Kubernetes、CRI-O、Cilium、Gateway API、PostgreSQL 的實際版本與設定；Deployment、Pod、Service、EndpointSlice、Gateway、HTTPRoute 的完整物件及 status。用來確認實驗究竟跑在什麼環境。 |
| 原始時間序列 | Pod deletion timestamp、EndpointSlice 條件變化、入口後端選擇、App 收到 SIGTERM 和結束的時間，以及用戶端請求、重連、事件接收紀錄。用來重建事件順序。 |
| 原始網路與協定資料 | SSE HTTP 回應、事件欄位、重連請求與 `Last-Event-ID`，以及需要時的封包或連線追蹤。用來區分規範、代理行為與測試程式的解讀。 |
| 資料庫原始紀錄 | 交易結果、訂單與叫號資料、測試識別碼及時間；必要時包括鎖等待與資料庫日誌。用來獨立對帳。 |
| 規範與版本對應文件 | Kubernetes 終止與 EndpointSlice 文件、Gateway API 規範、**實際 Cilium 版本**的文件與設定、WHATWG SSE 標準、PostgreSQL 交易及 `LISTEN`／`NOTIFY` 文件。必要時查對應版本原始碼。 |
| 原始測試程式與設定 | App、Rush Hour、manifest、映像檔 digest，以及實際執行的命令和參數。實作完成後，才能核對量測是否真的符合設計。 |

特別值得回到原始規範的是兩個競態：PostgreSQL 明確指出初次 `LISTEN` 有競態，建議先讓 `LISTEN` 生效，再以新的交易檢查狀態；SSE 的事件 ID 與重連行為則應以標準和實際瀏覽器測試為準。[PostgreSQL `LISTEN`](https://www.postgresql.org/docs/current/sql-listen.html)、[WHATWG Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html)

## 3. 具體方法和工具

| 方法 | 可用工具 | 要回答的問題 |
|---|---|---|
| 建立時序圖與不變條件 | 手動畫時序圖；以 `client_ref`、`order_id`、`ready_seq`、Pod UID、量測編號串接紀錄 | 什麼必須始終成立？哪些事件只知道先後順序，哪些時間不可直接比較？ |
| 觀察控制平面 | `kubectl get ... -o yaml`、`kubectl get ... --watch`、`kubectl rollout status`、Pod 與 EndpointSlice 紀錄 | 更新實際何時開始、哪個 Pod 終止、endpoint 如何變化？ |
| 觀察資料平面 | Cilium／Envoy 的可用日誌與可觀測工具；必要時 `tcpdump`、`curl -N -v` | 請求實際進到哪個 Pod？SSE 在哪裡斷線？注意缺少證據時不把相關性直接當因果。 |
| 受控故障注入 | 測試專用同步點或可控代理；在提交前後、回應前、SSE 交接期間暫停或斷線 | 能否穩定重現「已提交但沒收到回應」及補送競態？ |
| 協定交叉驗證 | 真正的瀏覽器 `EventSource`、瀏覽器開發者工具、`curl` 原始串流 | `hello`、`shutdown`、`retry`、事件 ID 與重連是否符合預期？ |
| 獨立對帳 | `psql` 與獨立查詢；比對資料庫紀錄及各看板收到的事件集合 | 是否重複建立訂單、漏號、重複顯示或順序錯誤？未知項目是否被保留？ |
| 控制變因與重複實驗 | 既有 `measure.sh`、Rush Hour；記錄參數、隨機種子、版本與每次原始結果 | 機制改變前後有何差異？結果是否穩定？ |
| 時間與負載校正 | 單調時鐘量測同一程序內的時間差；記錄主機資源、請求延遲及負載產生速率 | 單一主機上的節點和負載產生器是否互相爭搶資源，影響結論？ |

實驗不必追求大量組合：每個核心主張先設一個基準、一個只改該機制的對照，加上能穩定觸發關鍵時序的案例。自然負載重複多次並呈現每次結果與樣本數；「觀察到零次」要照實報告，不能宣稱機率為零。

## 4. 除了你我之外，什麼可以證明結果正確？

嚴格來說，有限次實驗不能證明所有環境下永不出錯；但可以建立**可獨立檢查、可反駁的證據鏈**：

1. **規範與實作文件**：逐項指出哪些結論來自 Kubernetes、SSE 或 PostgreSQL 的規範，哪些依賴 Cilium 的特定版本與設定；引用原始來源，不把一般規範直接當成環境實測結果。
2. **獨立的測試預言機**：用資料庫事實、瀏覽器接收紀錄與入口／App 紀錄互相比對；不只依賴產生成績單的程式自行判分。
3. **可重現的反例測試**：故意關閉補送或冪等機制，確認測試確實能抓到漏號或重複訂單；打開後，在相同受控時序下驗證預期不變條件。
4. **第三方重跑**：讓另一位講師或工程師依照固定版本、命令、初始條件與驗收標準重跑，取得原始紀錄，而非只檢查摘要。
5. **可稽核的證據包**：保存 manifest、版本與 digest、實驗參數、原始事件、查詢、成績單和失敗案例。明確列出量測限制、未觀察到的情況與仍待驗證的假設。

## 修改後的題目

> 我在教 Kubernetes CI/CD。請針對第一階段課程，設計一個**更深入、但範圍不更大**的題目：使用飲料店點餐 App 與 SSE 取餐叫號看板，研究滾動更新期間，短請求 `POST /orders`、`POST /orders/{id}/ready` 與長連線如何受到影響，以及如何驗證修正是否有效。
>
> 環境為 Kubernetes v1.37.1、CRI-O、Cilium Gateway API；Kubernetes 節點是同一台主機上的 Podman container。現有設計位於 `design-v2/`，實作計畫位於 `plan.md`。請把這些文件視為現況與待驗證假說，不預設每個機制、預期效果或數值都已成立。設計目前尚未實作。
>
> 請完成以下工作：
>
> 1. **界定核心問題與保證。** 分別定義請求送達、資料庫提交、用戶端收到回應、重試、SSE 斷線與重連、事件補送及看板收到事件。列出可觀察的不變條件、必要假設、失敗模式，以及無法判定時應如何報告。區分協定保證、應用程式設計保證和特定環境的實測結果。
>
> 2. **從原始素材建立證據。** 指出需要取得的實際版本與設定、Kubernetes 物件及狀態、控制平面和資料平面時間序列、原始 HTTP／SSE 記錄、資料庫紀錄，以及對應版本的官方規範、文件或必要的原始碼。說明每份素材能支持什麼結論，以及不能單獨證明什麼。
>
> 3. **設計最小而有辨識力的實驗。** 保留現有五個教學步驟作為候選，但檢查它們是否真的各自驗證一個機制。對每個核心假說，提供基準與控制變因的對照；另設可重現的關鍵時序案例，至少涵蓋「訂單提交後、回應前斷線」與「SSE 登記、補送和即時推送交接時有新叫號」。寫出操作方式、量測點、預期觀察、可能反例及失敗／未知的判定。
>
> 4. **驗證量測與結果。** 具體說明如何用真正的瀏覽器 `EventSource`、原始 HTTP 串流、獨立資料庫查詢及必要的入口／App 紀錄交叉驗證 Rush Hour；並以刻意關閉機制的反例，確認測試能偵測問題。說明如何重複量測、呈現樣本與不確定性，以及如何避免把單次零失敗解讀成永遠不失敗。
>
> 5. **提出可教、可驗收的課程題目。** 給出學生需要預測、操作、觀察和解釋的內容；將精密故障注入或環境診斷放在適當的講師或自動化支援中。列出驗收標準、講師所需證據包、第三方重跑方式，以及因單一主機、單一資料庫實例和版本設定造成的結論邊界。
>
> 請使用具體工具、命令或測試手法支持建議，引用最接近原始規範與實際版本的來源。對尚未實測之處明確標示「待驗證」，不要虛構結果。不要擴充付款、會員、金絲雀部署、資料庫高可用等新功能；只有在直接支撐上述驗證時才增加工具或觀測能力。
