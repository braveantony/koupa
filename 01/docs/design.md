# Koupa 酷杯：第一階段設計文件

> 狀態：設計定案，尚未實作（2026-11-02）
> 標示「待實測」的項目，要等 tk8s 重建好、實際量測後才定案。

## 1. 課程主線

這門 Kubernetes CI/CD 課程用同一個範例應用 **Koupa 酷杯**（手搖飲料店的點餐與叫號系統）貫穿三個階段：

| 階段 | 技術主題 | 店裡的故事 |
|---|---|---|
| **01** | Rolling update（逐步用新版 Pod 換掉舊版 Pod 的升級方式）時，長連接和短連接的處理 | 下午茶尖峰時段系統要升級，點餐不能掉單，叫號不能漏號 |
| **02** | 程式進版、退版時，資料庫 schema 怎麼跟著變 | 每杯飲料要記錄「甜度、冰塊」，資料表要加欄位，出問題要能退版 |
| **03** | 用 Cilium Gateway API 分流做金絲雀部署（先把少量流量導到新版） | 夏季限定新品「旺來綠茶」上市，先開放給 10% 的客人 |

`01/`、`02/`、`03/` 各放一份**完整的快照**，學生可以從任何一個階段開始。01 定案後才複製到 02，02 的講義會列出跟 01 相比改了哪些檔案。

本文件只描述第一階段。

## 2. 命名與世界觀

| 項目 | 內容 |
|---|---|
| 店名 | **Koupa 酷杯**。Koupa 是希臘文的「杯子」（κούπα），念起來像 Kube，延續 Kubernetes 生態系用希臘文命名的傳統 |
| 技術名稱 | `koupa`，用在映像檔、Deployment、Service、HTTPRoute 和 namespace |
| 口號 | 微糖、去冰、零停機 |
| 菜單 | 滾動珍珠奶茶、Pod 沫紅茶、微服務綠茶、容器冬瓜茶 |
| 03 新品 | 旺來綠茶（鳳梨綠茶）。黃色呼應金絲雀，台語「旺來」也有生意興旺的意思 |
| 量測工具 | **Rush Hour**，技術名稱 `rush-hour`。模擬下午茶尖峰剛好碰上系統升級 |

## 3. 第一階段的教學目標

讓學生親眼看到 rolling update 時會發生的問題，再一步一步修好，並用數字證明每一步的效果：

- **短連接**：點餐 `POST /orders` 和出餐 `POST /orders/{id}/ready`，升級期間會失敗或重複下單。
- **長連接**：叫號看板的連線會在升級時中斷，斷線期間完成的訂單不會被叫到。

**教學原則**

- **先壞再修**：先部署什麼都沒處理的版本，讓問題出現，再逐步修正。
- **用數字證明**：每一步都用 Rush Hour 的成績單量化結果。
- **量到問題才加修正**：不刻意模擬問題（例如不故意讓 App 啟動變慢）。量不到的問題就不放進修正步驟，只在講師手冊裡說明。
- **學生只改 YAML**：程式端的修正事先寫好，用環境變數開關控制。每個開關對應的程式碼放在講義裡講解，讓學生看得懂，但不用自己寫。

## 4. 系統架構

```
主機（叢集外）
  podman run rush-hour
     │  HTTP
     ▼
Cilium Gateway（IP 由 Cilium 的 LoadBalancer IP 池分配）
     │
     ├──► koupa Pod 1 ┐
     ├──► koupa Pod 2 ├─ 3 個 Pod，平均分散在 3 個 worker 上
     └──► koupa Pod 3 ┘
              │
              ▼
        PostgreSQL（CloudNativePG 單節點）
          ・存菜單和訂單
          ・用 LISTEN/NOTIFY 通知所有 Pod「有訂單完成了」
```

| 項目 | 決定 | 理由 |
|---|---|---|
| 程式語言 | Go | 映像檔小、啟動快；處理關機訊號的程式短，放得進投影片 |
| 映像檔 | distroless（不含 shell 的極簡映像檔），約 20 MB | 小、安全。`preStop` 改用 Kubernetes 內建的 `sleep` 動作，不需要 shell |
| App Pod 數量 | 3 個 | 只有 1 個 Pod 時，升級就是直接停機。有 3 個 Pod，升級時新舊 Pod 才會同時存在，才會出現本階段要教的問題 |
| 升級方式 | Kubernetes 預設的 rolling update，不另外調參數 | 步驟 0 就是「什麼都沒改」的真實樣子 |
| 資料庫 | CloudNativePG（簡稱 CNPG，在 Kubernetes 上管理 PostgreSQL 的 operator）單節點，資料放 `local-path` | 資料庫不是本階段的重點，越單純越好 |
| 長連接 | SSE（Server-Sent Events，伺服器單向推送資料給瀏覽器的 HTTP 長連線） | 看板只需要接收；瀏覽器內建自動重連，重連時會帶上最後收到的事件編號 |
| 入口 | 01 就走 Cilium Gateway | 三個階段用同一個入口；Gateway 會切斷閒置的長連接，本身就是該教的內容 |
| 連線協定 | HTTP，Gateway 不設網域名稱，直接用 IP 連 | 01 不處理憑證，避免分心 |
| namespace | `koupa` | 和 App 名稱一致 |

### 為什麼需要跨 Pod 通知

```
1. 叫號看板連到 Pod 1
2. 店員按「058 號完成」，這個請求被分到 Pod 2
3. Pod 2 沒有通知 Pod 1 → 看板不會跳出 058 號
```

所以每個 Pod 啟動後都會 `LISTEN` 同一個頻道。任何一個 Pod 把訂單標記完成時就送出 `NOTIFY`，所有 Pod 都會收到，再推給連在自己身上的看板。

`NOTIFY` 送出後不會保留：Pod 剛好沒在 `LISTEN` 的那段時間，通知就收不到。所以看板重連後一定要回資料庫補查（見步驟 3），不能只靠通知。

## 5. App 功能

### 5.1 三個頁面

| 頁面 | 連線 | 行為 |
|---|---|---|
| 點餐頁 | 短連接 | 一張單可以點多種飲料、每種可以點多杯，會顯示合計金額。送出 `POST /orders` 後拿到號碼牌 |
| 廚房頁 | 短連接 | 列出製作中的訂單和內容，按「完成」送出 `POST /orders/{id}/ready` |
| 叫號看板 | 長連接（SSE） | 整張單都完成才叫號，畫面顯示「請 058 號取餐 🧋」 |

不做付款、會員、外送，因為這些和三個階段的主題無關。

### 5.2 v1 與 v2

v2 比 v1 多一個真的功能：**售完標示**。

- 廚房頁可以把某個品項設成「售完」，例如珍珠煮完了；
- 點餐頁會把售完的品項變成灰色、不能點；
- 送出含有售完品項的訂單時，伺服器會拒絕。

這個功能只用到 `menu_items` 現有的 `available` 欄位，不用改資料表（改資料表是 02 的主題）。

**學生怎麼知道看板連到哪個版本**：看板的網頁只在一開始載入一次，SSE 重連時網頁不會重新載入。所以每次 SSE 連線建立時，伺服器會先送一個事件告訴看板自己的版本，看板角落顯示「服務版本：v2」。

**升級期間新舊版並存**：rolling update 期間，客人可能被分到還沒換掉的 v1 Pod。v1 不會檢查售完，所以售完的品項還是可能被點到。退版回 v1 時，資料庫裡的售完標記還在，但 v1 會忽略它。這是新舊版並存的真實狀況，在講師手冊裡當作補充說明，為 02 的「新舊版程式同時運作」鋪路；成績單不計算這一項。

**後續候選（先記錄，不做）**：看板多一欄「製作中」，左邊列出製作中的號碼，右邊列出請取餐的號碼。這個功能要讓 SSE 多送「新訂單」事件，升級期間新舊版並存時會多出事件相容性的問題，所以不放進 01。

### 5.3 號碼牌

號碼從 001 到 999，用完再從 001 開始，由資料庫產生，所以 3 個 Pod 同時收單也不會重號。

因為號碼會循環，看板補號用的「事件編號」不能用號碼牌，要用另一個只增不減的編號（見 5.4 的 `ready_seq`）。

### 5.4 資料表

```
menu_items   id │ name（品名）│ price（價格）│ available（是否供應中）

orders       id │ number（號碼）│ status（製作中／完成）│ total（總金額）
             │ created_at（建立時間）│ ready_seq（完成順序）│ client_ref（防重複代碼）

order_items  order_id │ menu_item_id │ quantity（數量）│ unit_price（下單時的單價）
```

- `ready_seq`：訂單標記完成時，由資料庫配發一個只增不減的編號，當作 SSE 的事件編號。
- `client_ref`：每次送出訂單前，由點餐頁產生的隨機字串。不論防重複下單的開關有沒有打開都會記錄，Rush Hour 才算得出重複訂單。
- 02 會把甜度、冰塊加在 `order_items` 上，因為同一張單裡每一杯可以不同。

### 5.5 建表方式

用 golang-migrate（資料庫 migration 工具：照編號依序執行 SQL 檔，並記錄執行到哪一號）建表，以 Kubernetes Job 執行。部署時先跑 migration Job，成功後才部署 App。

```
01/migrations/
  000001_init.up.sql   / 000001_init.down.sql    建立 3 張表
  000002_menu.up.sql   / 000002_menu.down.sql    放入 4 個品項
```

不讓 App 啟動時自己建表，因為 3 個 Pod 同時啟動會搶著建表，02 正好要教為什麼不能這樣做。01 只要讓學生知道「部署前先跑一個 Job 建表」；02 在同一套 migration 後面接著加檔案。

## 6. 修正步驟

用 Kustomize（在共用的 YAML 上疊加差異的工具）一層疊一層，每一步的資料夾只放這一步的改動：

```
base ◄── step-1 ◄── step-2 ◄── step-3 ◄── step-4
base ◄── idle-lab（獨立的小實驗）
```

想看某一步完整的 YAML，可以執行 `kubectl kustomize k8s/steps/step-3`。

| 步驟 | 改什麼 | 預期成績單變化 |
|---|---|---|
| **閒置斷線小實驗** | 打開 `SSE_HEARTBEAT` | 沒在升級，看板也會被 Gateway 切斷；加上心跳後不再斷線 |
| **0** | 什麼都沒做（基準） | 失敗、漏號、重複都有 |
| **1** | 加上 `preStop` 的 `sleep` | 「Pod 正在關閉，Gateway 還在把客人送過來」的失敗消失 |
| **2** | 打開 `GRACEFUL_SHUTDOWN`，設定 `terminationGracePeriodSeconds`（關機寬限時間） | 短連接失敗接近 0；看板從被硬拔改成被主動請去重連，但還是會漏號 |
| **3** | 打開 `RESUME_FROM_LAST_ID` | 看板重連後補回漏掉的叫號，漏號歸 0 |
| **4** | 打開 `IDEMPOTENCY_KEY` | 客人重送不會重複下單，重複訂單歸 0 |

### 6.1 閒置斷線小實驗

看板連著但一直沒有叫號時，Gateway 會把它當成閒置連線切斷，即使根本沒在升級。這個問題不是升級造成的，放進修正步驟會干擾數字，所以獨立成小實驗，放在步驟 0 之前，讓學生先認識「長連接本身就很脆弱」。

打開 `SSE_HEARTBEAT` 後，App 會定期送出 SSE 註解行（以 `:` 開頭，瀏覽器會忽略）當作心跳。

**待實測**：Cilium Gateway 預設多久切斷、是因為閒置還是連線總時間太長、心跳間隔要設多少。如果切斷原因是總時間太長，心跳就無效，要改成調整 HTTPRoute 的逾時設定，小實驗的內容也要照實際結果改寫。

### 6.2 步驟 0：基準

App 沒有處理關機訊號。Pod 被刪除時，Go 程式收到 SIGTERM 就立刻結束：處理到一半的請求直接中斷，看板的連線也被硬拔。

### 6.3 步驟 1：preStop

Pod 被刪除後，Gateway 和各節點要過一小段時間才會知道「這個 Pod 不要再送客人過來」。這段時間內如果 App 已經結束，送過來的請求就會失敗。

`preStop` 加上 `sleep`，讓 Pod 先等幾秒、等流量不再進來，Kubernetes 才送出 SIGTERM。

### 6.4 步驟 2：Graceful shutdown

打開 `GRACEFUL_SHUTDOWN` 後，App 收到 SIGTERM 時會：

1. 停止接受新連線；
2. 把處理到一半的短連接做完；
3. 主動結束每一條 SSE 連線，讓看板自動重連到其他 Pod；
4. 全部完成後才結束程式。

SSE 連線不會自己結束，Go 的 `http.Server.Shutdown` 也不會等它，所以程式要主動通知每一條 SSE 連線收尾。

**不採用的做法**（只在講師手冊口頭說明）：

- 把關機寬限時間設很長，等看板自己離開。看板永遠不會自己離開，升級會卡住。
- 多台看板錯開時間重連，避免同時擠到新 Pod。這是實務上常見的細節，當作延伸內容。

### 6.5 步驟 3：斷線重連後補號

瀏覽器重連 SSE 時，會自動在 `Last-Event-ID` 標頭帶上最後收到的事件編號，也就是 `ready_seq`。打開 `RESUME_FROM_LAST_ID` 後，App 會先從資料庫補送所有 `ready_seq` 比它大的叫號，再繼續推送新的。

```
1. 看板顯示到 057 號
2. 升級時看板連的 Pod 被關掉，連線中斷
3. 斷線期間 058、059 號完成
4. 看板自動重連，告訴新的 Pod：「我最後收到的是 057」
5. 新的 Pod 從資料庫查出 058、059 補送 → 沒有漏號
```

開關關閉時，App 不理會 `Last-Event-ID`，058、059 就會漏掉。

### 6.6 步驟 4：重送不重複下單

就算前面都做對了，短連接還是可能遇到這種情況：

```
1. 客人送出訂單，訂單已經寫進資料庫（058 號）
2. 回應還沒送回去，連線就斷了
3. 客人看到「失敗」，再送一次
4. 資料庫多一張 059 號 → 同樣的飲料做兩份
```

打開 `IDEMPOTENCY_KEY` 後，App 收到訂單會先用 `client_ref` 檢查：已經建立過就回傳原本的號碼，沒有才新增。出餐 `POST /orders/{id}/ready` 本身重送也不會出事（同一張單標記兩次完成，結果一樣），所以只有點餐需要處理。

這一步放在最後，要讓學生知道：Kubernetes 能把失敗降到很少，但沒辦法降到零，程式也要能安全地重送。

### 6.7 readinessProbe（待實測）

修正步驟裡沒有 readinessProbe（Kubernetes 用來判斷 Pod 是否準備好接客的檢查），因為 Go 程式啟動很快，預期量不到「新 Pod 還沒準備好就接客」造成的失敗。

實作完成後先在 tk8s 跑步驟 0。如果真的量到這類失敗，例如 App 還沒連上資料庫就開始接客，就把它加進修正步驟，並附上實測數據說明原因。量不到的話，只在講師手冊說明為什麼這個 App 不需要。

## 7. 量測

### 7.1 measure.sh

Pod 關機時怎麼處理，是由**被關掉的那個 Pod** 的設定決定的。如果直接修改開關來觸發升級，被關掉的是開關還沒打開的舊 Pod，量到的數字還是壞的。所以每一步都分成兩段：

```
measure.sh <步驟>
  1. 套用這一步的設定，等升級完成（這次不量）
  2. 查出 Gateway 的 IP
  3. 在背景執行 podman run rush-hour --target http://<Gateway IP>
  4. 觸發要量的版本變更：
     ・目前是 v1 → 升級到 v2（上架售完功能）
     ・目前是 v2 → 退版回 v1（假設售完功能有 bug，緊急退版）
  5. 版本變更完成後，等最後幾個叫號送到，印出成績單
```

升級和退版在實務上都必須零停機，所以兩個方向都要量。每一步量的是哪個方向，由當時叢集上的版本決定，成績單上會標明。

Rush Hour 在主機上用 podman 執行，從叢集外經過 Gateway 連進來，跟真實客人走同一條路，也不會占用 worker 的資源。

### 7.2 Rush Hour

**預設負載**（都可以用參數調整，例如 `--rate 50`）：

| 角色 | 預設 |
|---|---|
| 客人 | 每秒 20 張訂單，每張隨機 1～4 杯；失敗時用同一個 `client_ref` 重試 1 次 |
| 廚房 | 訂單送出後隨機 1～3 秒標記完成 |
| 看板 | 3 台，各自用 SSE 連線，記下收到的每個叫號 |

**成績單**：

```
┌──────────── Rush Hour 成績單 ────────────┐
│ 送出訂單：      1,200 筆                  │
│ 失敗：             37 筆 (3.1%)           │
│ 重複訂單：          4 筆                  │
│ 看板漏號：   看板 1 漏 5 個               │
│              看板 2 漏 0 個               │
│              看板 3 漏 3 個               │
│ 看板斷線次數：      6 次                  │
└──────────────────────────────────────────┘
```

（數字僅為示意。）

- **漏號**：量測結束後，透過 App 的 API 查出資料庫裡這段時間內完成的訂單，和每台看板實際收到的叫號比對。
- **重複訂單**：同一個 `client_ref` 在資料庫裡有兩張以上的訂單。

Rush Hour 在叢集外，連不到資料庫，所以這兩項都透過 App 提供的 API 查詢。

## 8. 環境需求

每個學生一套和 tk8s 相同規格的叢集：

- 1 個 control plane＋3 個 worker，節點跑在 podman container 裡；
- Cilium，並啟用 Gateway API、LoadBalancer IP 池和 L2 廣播；
- 預設的 StorageClass `local-path`；
- 主機上可以執行 podman，而且主機連得到 Gateway 分配到的 IP。

學生講義的第一步是自己安裝 CNPG operator（固定版本），讓學生知道資料庫是怎麼來的。CNPG 在 02 也可能用到。

YAML 不寫死 IP，`measure.sh` 會自動查 Gateway 的 IP。

## 9. 映像檔
