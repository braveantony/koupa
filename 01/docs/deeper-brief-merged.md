## 題目

> **01：Pod 終止時，流量和程式各走各的**
>
> 在 tk8s 上，用可重複、可推翻的實驗，讓學生親眼看到：Pod 終止時，「入口停止送流量」和「程式開始關機」同時發生、互不等待。接著用證據說明，每一步修正之後，短連線（點餐、出餐）和長連線（SSE 叫號看板）的每一個結果，為什麼成功、為什麼失敗，或為什麼無法判定。

## 要求

### 1. 先定義「結果」，再量測

一張單、一個叫號，分成幾個可以各自觀察的結果，不混成一個「失敗」：

| 對象 | 分開觀察的結果 |
|---|---|
| 點餐 | 請求有沒有送到 App → 交易有沒有提交 → 客人有沒有收到回應 → 有沒有重試 → 最後資料庫有幾張單 |
| 出餐 | 請求有沒有送到 → 有沒有配發 `ready_seq` → 店員有沒有收到回應 |
| 叫號 | 看板有沒有斷線 → 重連後有沒有補送 → 每台看板最後有沒有收到每個叫號 |

- 每一項都寫出不變條件，例如「同一個 `client_ref` 最多一張單」「看板收到的編號遞增、不重複」；
- 判斷不出來的結果標成「未知」，並寫明原因，不當成成功，也不當成失敗；
- 每個保證都標明它的來源：協定規範保證（例如 SSE、PostgreSQL）、App 設計保證，或只是這個環境的實測結果。

### 2. 每次量測都產生因果時間線

從叢集的原始紀錄產生一條時間線，包含：Pod 開始終止、SIGTERM、EndpointSlice 標成 terminating、入口實際拿掉這個 Pod、最後一個請求進來、程式結束、看板斷線和重連。

- 每個時間點都要有原始紀錄作為依據，不是推論；
- 用 `client_ref`、`order_id`、`ready_seq`、Pod UID、量測編號，把各來源的紀錄串在一起；
- 所有節點共用同一台主機的時鐘，跨來源的時間戳可以直接比較；同一個程式內的時間差，用單調時鐘量。

### 3. 參數用量的，不用猜

- `preStop` 秒數，等於實測「入口停止送流量」延遲的上緣，再加緩衝；
- 閒置逾時，從 Envoy 的即時設定讀出，再決定心跳間隔；
- 推導過程和原始數據寫進實測紀錄。

### 4. 兩種實驗，回答不同的問題

| 實驗 | 回答的問題 | 做法 |
|---|---|---|
| **自然負載**（Rush Hour） | 真實升級時，各步驟的效果差多少 | 固定速率送單（不等上一張回應），每個條件至少重複 5 次，回報每次結果、中位數和範圍 |
| **關鍵時機**（受控注入） | 保證在最壞的時機是否仍然成立 | 用測試專用的暫停點，穩定重現下面這些時機 |

關鍵時機至少包含：

- 訂單已經提交、回應還沒送出時，連線被切斷；
- 請求處理到一半，Pod 開始終止；
- 看板登記之後、查補送上界之前，有新的叫號提交；
- 看板寫入卡住時，Pod 開始終止。

另外有兩組對照，不成立時整個實驗就不成立：

- **不升級的對照組**：必須 0 失敗。不是的話，表示雜訊來自量測工具或環境；
- **步驟 0 基準組**：必須量到問題。量不到的話，表示實驗偵測不到問題，後面的「修好了」就沒有意義。

五個教學步驟保留為候選，但每一步都要確認只驗證一個機制。實測可以推翻某一步的效果或順序。

### 5. 失敗用原始證據分類

依 Envoy 回應旗標和 access log、App log、資料庫對帳，把失敗分成：

- 入口把請求送到正在關的 Pod；
- 請求處理到一半被切斷；
- 量測工具自己的問題，例如逾時設定、主機資源被搶。

Rush Hour 的數字要能和 Envoy stats 對得上。同時記錄主機的 CPU 和記憶體，因為節點和量測工具在同一台主機上。

### 6. 量測工具本身要被驗證

- **交叉檢查**：用真正的瀏覽器 `EventSource` 和 `curl -N` 看原始串流，確認 Rush Hour 對 SSE 的解讀正確；用另一套負載工具（k6 或 vegeta）量同一步，結論的方向要一致；
- **反例測試**：刻意關掉補送或防重複機制，或讓 App 故意漏送一個叫號，確認對帳程式抓得到；
- **誠實報告**：「觀察到 0 次」照實寫成「N 次量測中觀察到 0 次」，不寫成「不會發生」。

### 7. 能用在其他情況

同一套修正，在 `kubectl drain` 和縮減 Pod 數量時也要成立。學生學的是 Pod 終止，不只是滾動更新。

### 8. 可教、可驗收、可重現

- **學生做的**：先預測，再操作、看成績單和時間線，最後解釋（預測 → 觀察 → 解釋）。關鍵時機的注入和環境診斷，交給講師示範或自動化測試；
- **證據包**：每次量測保存 manifest、版本和映像檔 digest、參數、原始紀錄、查詢、成績單和失敗案例；
- **第三方重跑**：另一個人在全新的叢集上，只照 README 操作，得到相同的定性結論，並交回原始紀錄，不只是摘要；
- **上游依據**：每個關鍵假設都附 Kubernetes、Cilium（實際版本）、Envoy、Go、WHATWG SSE、PostgreSQL 的文件或原始碼出處；
- **結論邊界**：寫明單一主機、單一資料庫實例、特定版本和設定造成的限制。

## 原始素材清單

| 素材 | 要回答的問題 |
|---|---|
| Kubernetes Pod 終止流程文件、EndpointSlice terminating 狀態（KEP-1672）、kubelet 原始碼 | `preStop` 和 SIGTERM 的順序；終止中的 Pod 會不會繼續收流量 |
| 實際 Cilium 版本的 Gateway API 轉換原始碼，以及 tk8s 上 Envoy 的即時設定 | 入口的逾時、重試設定，多久才拿掉終止中的 Pod |
| Envoy 文件：回應旗標、各種逾時 | 每一個 503 屬於哪一種失敗 |
| Go `net/http` 原始碼：`Shutdown`、`RegisterOnShutdown`、用戶端重試規則 | 關機和重試行為是否和設計假設一致 |
| WHATWG HTML 規格的 SSE 章節，加上實際瀏覽器測試 | `Last-Event-ID`、`retry`、事件派送規則 |
| PostgreSQL 文件：`LISTEN` 的競態、`NOTIFY` 的送達時機、sequence、advisory lock | 叫號編號保證的依據 |
| CNPG 文件 | 有哪些操作會重啟資料庫、干擾量測 |
| 實際叢集的版本和物件狀態（Deployment、Pod、EndpointSlice、Gateway、HTTPRoute 的完整 YAML 和 status） | 實驗究竟跑在什麼環境 |
| 每次量測的原始紀錄：events、EndpointSlice 變化、Hubble 流量、Envoy access log 和 stats、App 和 Rush Hour 的 JSONL | 重建時間線，不靠推論 |

## 工具

| 用途 | 工具 |
|---|---|
| 控制平面 | `kubectl get -w`（events、endpointslice）、`kubectl get -o yaml`、`kubectl rollout status` |
| 資料平面 | `hubble observe`、Envoy 管理介面（config dump、stats）、必要時 `tcpdump` |
| 協定 | 瀏覽器 `EventSource` 和開發者工具、`curl -N -v` |
| 資料庫 | `psql` 獨立查詢 |
| 負載 | Rush Hour（固定速率）、k6 或 vegeta 交叉比對 |
| 故障注入 | 測試專用暫停點、`kill -STOP`、暫停 `LISTEN` 連線、慢速看板 |
| 正確性 | `go test -race`；把看板收到的序列和資料庫紀錄逐一比對的檢查程式（概念同 Jepsen） |
